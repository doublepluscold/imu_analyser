# Завдання: прошивки ESP для бездротового IMU-демо (slave ESP-01 і master ESP32-S3)

Ти пишеш прошивки для двох плат. Програма-приймач на ноутбуці (`imuview`, Python) уже готова й чекає UDP-датаграми в чітко визначеному форматі. Твоя задача - зробити так, щоб байти MTData2 від IMU-модулів доходили до неї.
Відповідай і коментуй українською, код і імена англійською. У тексті використовуй дефіс, не довге тире. Роби просто й зрозуміло, без екзотичних трюків і неперевірених хаків.

---

## 1. Що за система

```
IMU-модуль #1 --UART--> ESP-01 (slave) --ESP-NOW--\
IMU-модуль #2 --UART--> ESP-01 (slave) --ESP-NOW---> ESP32-S3 (master) --Ethernet/UDP--> ноутбук (imuview)
IMU-модуль #N --UART--> ESP-01 (slave) --ESP-NOW--/
```

- **IMU-модуль**: STM32H743 + датчик, сам шле потік **Xsens MTData2** по UART, 115200 8N1, без запиту. Ми його не чіпаємо.
- **Slave (ESP-01, ESP8266)**: слухає UART модуля, вирізає цілі кадри MTData2, кожен кадр шле по ESP-NOW майстрові. **Усі slave мають одну й ту саму прошивку.** Ніякого ID в прошивці немає.
- **Master (ESP32-S3)**: приймає ESP-NOW від усіх slave, сам видає кожному модулю `module_id` за порядком підключення (перший - 1, другий - 2...), загортає кадр у датаграму й шле UDP на ноутбук по Ethernet.
- **Ноутбук**: лише приймає (`UdpSource`), нічого не відповідає. Розбирає MTData2, калібрує, показує, пише лог.

## 2. Жорсткі правила

1. **Тільки слухати UART модуля.** На тому ж UART модуля сидять OTA-бутлоадер і командний парсер, випадковий байт може зіпсувати прошивку модуля. Тому:
   - slave **ніколи не пише** в UART, що йде до модуля;
   - у схемі до **RX модуля** ESP-01 **не підключається взагалі** (тільки TX модуля -> RX ESP-01 і спільна земля). Пам'ятай: ESP8266 при старті друкує діагностику на UART0 TX (74880 baud) - це була б каша в бутлоадері. Якщо в коді є `Serial.begin`, то лише для читання; діагностику виводь не в цей UART (див. п. 4.6). Запиши це попередження у README прошивки.
2. **Без SWD/JTAG і будь-яких дій з модулем.** Тільки читання потоку.
3. **Рівні напруги.** Модуль виводить RS-232 через ADM3232E; ESP-01 це 3.3 В TTL. Підключати треба до TTL-виходу (TX мікроконтролера до ADM3232E), а не до RS-232. Якщо інженер хоче інакше, зупинись і спитай (див. п. 9).
4. **ESP-NOW приймач (master) не відповідає payload-ом і не керує модулями.** Жодних команд вниз по ланцюжку.
5. **Ноутбук нічого не отримує, крім UDP від master.** Master не мусить слухати UDP. Він лише шле.
6. Датаграма ВІДПОВІДАЄ формату з п. 3 байт у байт. Програма на ноутбуці відкидає все, що не збігається.

## 3. Формат UDP-датаграми (master -> ноутбук)

Джерело істини: `src/imuview/netproto.py`. Little-endian.

```
offset size  поле
0      2     magic = 'I' 'V'  (0x49 0x56)
2      1     version = 1
3      1     module_id (1..255)
4      2     seq  u16 LE, лічильник датаграм цього модуля, з переходом 65535 -> 0
6      2     len  u16 LE, кількість байтів MTData2 далі
8      len   сирі байти MTData2 ОДНОГО модуля, звичайно рівно один цілий кадр
```

- Один кадр MTData2 на датаграму. IMU-кадр 94 байти, GpsSol 60 байтів. `len` має збігатися з реальною довжиною, інакше датаграма відкидається.
- `seq` рахує **master окремо для кожного `module_id`**, з 0, по 1 на кожну відправлену датаграму. За пропусками `seq` ноутбук рахує втрати.
- `module_id` 0 зарезервований для USB-serial на ноутбуці, master його не використовує.
- Максимальний payload 1400 байтів, але реально ~100.

**Тестовий вектор** (module_id 3, seq 1, payload `FA FF 36`):
`49 56 01 03 01 00 03 00 FA FF 36`

Перевірка Python-ом: `uv run python -c "from imuview.netproto import encode_datagram as e; print(e(3,1,bytes([0xfa,0xff,0x36])).hex(' '))"`.

**Мережа за замовчуванням:** master `192.168.50.2/24`, ноутбук `192.168.50.1`, UDP порт **5005**. Прямий кабель master - ноутбук. Адреса призначення й порт - константи в `config.h`. За бажання можна слати на broadcast `192.168.50.255` (тоді адреса ноутбука не потрібна), зроби це перемикачем у конфігу.

## 4. Slave: ESP-01 (ESP8266)

### 4.1 Що робить
1. Читає байти з UART (`RX` = GPIO3) на **115200 8N1**. Збільши буфер прийому (напр. 1024 байти), щоб не втрачати при паузах.
2. Збирає кадри MTData2 (п. 5) і для **кожного валідного кадру** шле один ESP-NOW пакет на master. Payload пакета = кадр байт у байт (`FA FF 36 LEN ... CS`), без жодних заголовків.
3. Нічого не шле в UART.

### 4.2 ESP-NOW
- Wi-Fi режим STA, **фіксований канал** (`WIFI_CHANNEL` у `config.h`, за замовчуванням 1), однаковий на master і slave. До жодної точки доступу не підключатись.
- Одержувач: MAC master (`MASTER_MAC` у `config.h`). Якщо не задано - слати на broadcast `FF:FF:FF:FF:FF:FF` (master розпізнає slave по MAC відправника). Unicast краще (є ACK і повтор на рівні MAC), broadcast простіше для першого запуску; підтримай обидва.
- Кадр до 250 байтів влазить в один пакет. Кадри довші за 250 байтів (extended) **пропускай і рахуй** (у цьому потоці їх не очікується).
- Не блокуй читання UART очікуванням `send callback`. Використай невелику кільцеву чергу кадрів (напр. 8-16 кадрів). Якщо черга повна - **викинь найстаріший кадр** і збільш лічильник `dropped`.

### 4.3 Швидкодія
Потік модуля близько 100 IMU-кадрів/с + 5 GpsSol-кадрів/с (~11 КБ/с, лінія завантажена на ~85%). Читай UART у `loop()` без `delay()`, у кожному проході забирай усе, що є.

### 4.4 Статистика
Лічильники: байтів прочитано, валідних кадрів, кадрів з поганою сумою, кадрів надто довгих, відправлено, помилок відправки, викинуто з черги. Раз на секунду друкуй один рядок (див. п. 4.6).

### 4.5 Живлення і старт
Автоматично стартує, нічого не чекає. Для налагодження на столі достатньо USB-UART адаптера на ESP-01.

### 4.6 Діагностика, не чіпаючи UART модуля
ESP-01 має лише один повноцінний UART (пінів для `Serial.swap()` на платі не виведено). Тому:
1. У бойовому режимі (`DEBUG_LOG 0`) на UART **нічого не друкується**, TX ESP-01 ні до чого не підключений.
2. У режимі налагодження (`DEBUG_LOG 1`) статистика йде на TX ESP-01 на USB-UART адаптер, а потік модуля на RX подається з окремого джерела. TX ESP-01 при цьому **не з'єднаний** з RX модуля.
3. Світлодіод GPIO2 мигає при кожному надісланому кадрі (працює в обох режимах).
Опиши це в README так, щоб ніхто не з'єднав TX ESP-01 з RX модуля.

## 5. Розбір кадрів MTData2 (і slave, і master)

Кадр: `FA FF 36 LEN payload CS`.

| поле | байти | значення |
|---|---|---|
| preamble | `FA` | початок |
| BID | `FF` | |
| MID | `36` | MTData2 |
| LEN | 1 | довжина payload; якщо `0xFF`, то далі **2 байти big-endian** з реальною довжиною (extended) |
| payload | LEN | блоки даних |
| CS | 1 | контрольна сума |

- **Перевірка:** `(BID + MID + LEN + payload... + CS) & 0xFF == 0` (сума від байта `FF` до `CS` включно).
- Розміри: IMU-кадр 94 байти (`LEN`=89), GpsSol 60 байтів (`LEN`=55).
- Перед кожним кадром шукай `FA FF 36`. Якщо суму не пройдено - **зсунься на 1 байт** і шукай наступний синхробайт (ресинхронізація).

**Відомий дефект прошивки модуля (важливо):** 30-40% IMU-кадрів приходять з **поганою контрольною сумою** (гонка буферів у модулі, не лінія). Перші 3 кадри після кожного GpsSol погані на 85-97%. Тому:
- slave **відкидає кадри з поганою сумою** і рахує їх у лічильник; пересилати тільки валідні (це ~60 IMU-кадрів/с);
- не вважай це помилкою прошивки ESP;
- `FA FF` усередині даних практично не трапляється, але обробляй коректно (ресинхронізація по сумі).

Еталон реалізації: `src/imuview/protocol_mtdata2.py` (`Mtdata2Framer`), `vendor/mtdata2_decoder.py`, опис потоку в `docs/module-context.md` і `docs/system.md` (розділи 4, 6, 11).

## 6. Master: ESP32-S3

### 6.1 Що робить
1. Піднімає Wi-Fi STA на тому самому каналі (без підключення до AP) і ESP-NOW; реєструє callback прийому.
2. Піднімає **Ethernet**. ESP32-S3 не має вбудованого Ethernet MAC, тому очікується SPI-чіп **W5500** (див. п. 9, спитай, якщо інакше). Статична IP `192.168.50.2/24`.
3. На кожен ESP-NOW пакет:
   - валідує, що payload - це один цілий кадр MTData2 (`FA FF 36`, довжина, сума). Поганий пакет відкидає й рахує;
   - визначає `module_id` за MAC відправника (п. 6.2);
   - формує датаграму п. 3 з `seq` цього модуля і шле UDP на ноутбук.
4. Роздача ID не блокує передачі: новий slave отримує ID при першому ж валідному пакеті.

### 6.2 Таблиця ID
- Таблиця `MAC slave -> module_id`, максимум **8 модулів** (на стільки розрахований GUI; `MAX_MODULES` у `config.h`).
- Новий MAC отримує наступний вільний ID: 1, 2, 3... (за порядком першого валідного пакета).
- **Зберігай таблицю в NVS**, щоб після перезапуску master модулі мали ті самі ID (у GUI ID прив'язані до імен "Дрон 1", "Дрон 2").
- Скидання таблиці: утримання кнопки BOOT (GPIO0) 5 секунд при старті, або команда `reset_ids` у консолі (USB CDC).
- Якщо таблиця повна, пакети від нового MAC відкидаються, лог про це раз на 10 секунд.

### 6.3 Продуктивність
Очікувано до 8 модулів x (~65 IMU-кадрів/с + 5 GpsSol/с) = ~560 датаграм/с по ~100 байтів. Обробку роби без блокувань: callback ESP-NOW кладе пакет у чергу (FreeRTOS queue), окрема задача формує й відправляє UDP. Якщо черга повна, викидай найстаріше і рахуй.

### 6.4 Діагностика
Раз на секунду в USB-консоль рядок на модуль: `id`, MAC, прийнято/погані/відправлено/викинуто, останній RSSI. Плюс загальний рядок: стан Ethernet (link up, IP), розмір черги. Світлодіод: частіше мигає при трафіку.

## 7. Структура репозиторію і тести

Поклади в `firmware/` у корені проєкту `eps_imu_demo`:

```
firmware/
  README.md                  # схема підключення, попередження п. 2.1, збірка, прошивка
  common/                    # чистий C++ без залежностей від Arduino/ESP-IDF
    mtdata2_framer.h/.cpp    # збирач кадрів (п. 5)
    datagram.h/.cpp          # encode_datagram (п. 3)
    id_table.h/.cpp          # MAC -> module_id (п. 6.2), без NVS усередині
  slave_esp01/               # PlatformIO, Arduino-ESP8266
  master_esp32s3/            # PlatformIO, Arduino-ESP32 >= 3.0 (ETH.h з W5500) або ESP-IDF
  test/                      # `pio test -e native` на ПК
```

**Обов'язкові юніт-тести (запускаються на ПК, `pio test -e native`):**
- `mtdata2_framer`: валідний кадр, кадр з поганою сумою (відкидається, ресинхронізація на наступний), кадр розрізаний на довільні шматки, два кадри підряд, сміття між кадрами, extended LEN, кадр довший за буфер.
- `datagram`: байт у байт збігається з тестовим вектором п. 3 і з виводом `imuview.netproto.encode_datagram` (згенеруй кілька векторів Python-ом і встав у тест; `seq` з переходом через 65535).
- `id_table`: ID за порядком, повторний MAC той самий ID, переповнення таблиці, відновлення зі збереженого стану.

Код, що працює з радіо, UART і Ethernet, мусить компілюватися (`pio run`), навіть якщо залізо недоступне. Чесно пиши у відповіді, що перевірено (компіляція, юніт-тести), а що ні (робота на залізі).

## 8. Приймальні перевірки зі сторони ноутбука

Програма вже вміє приймати. Щоб перевірити твій master без slave, порівняй з еталоном, який імітує master:

```bash
uv run imu net --seconds 10 --no-record          # слухає UDP 5005, друкує статистику по модулях
uv run python tools/udp_master_sim.py --modules 3 --gps --host 192.168.50.1   # еталонний відправник
uv run imu gui --source udp                      # повний інтерфейс
```

Критерії для справжнього master:
- `imu net` показує всі підключені модулі з їхніми `module_id`, `bad_datagrams` = 0;
- `lost_datagrams` < 2% при нормальній відстані;
- у GUI модулі з'являються картками, з частотою ~60 Гц, без "немає даних";
- ID після перезапуску master ті самі.

## 10. Чого НЕ робити

- Не додавай шифрування, OTA-оновлення ESP, веб-інтерфейс, mDNS, MQTT - нічого, чого тут не описано.
- Не змінюй формат датаграми й не додавай у payload slave свої заголовки.
- Не змінюй жодного файла в `src/` і `tests/` проєкту (це приймач, він готовий). Якщо формат здається невдалим - опиши проблему окремим повідомленням, не змінюй мовчки.
- Не пиши в UART, що йде до IMU-модуля, за жодних умов.

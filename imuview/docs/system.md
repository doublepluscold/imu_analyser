# imuview: як влаштована програма і як з нею працювати

Стан на 2026-09-30 (кроки 1-5 плану зроблено, додано мульти-модульність і десктопний GUI, розділ 16).
Пов'язані документи:
- `docs/module-context.md` - що за пристрій, що про нього відомо, обмеження;
- `docs/CALIBRATION.md` - коротка інструкція, що записати для калібрації;
- `README.md` - короткий англомовний огляд.

---

## 1. Що це

`imuview` - програма на Python для IMU-модуля, з якого йде потік Xsens MTData2 по RS-232. Вона:

- слухає порт (тільки читає, нічого не надсилає);
- розбирає кадри, рахує помилки і відновлює час кожного кадру;
- застосовує калібрацію на стороні хоста, не змінюючи сирих даних;
- рахує власну орієнтацію (Mahony або Madgwick) і показує все в Rerun (3D-модель, графіки, журнал подій);
- записує кожну сесію повністю: сирі байти, розібрані потоки, метадані. Будь-яку сесію потім можна переглянути або перерахувати з іншим парсером чи іншою калібрацією;
- має інструменти калібрації в стилі Mission Planner: перевірка даних, гіро, осі. Accel, level, звіт і apply будуть на кроці 5;
- має симулятор, що генерує такий самий потік, як пристрій, включно з пошкодженими кадрами. На ньому тестується вся логіка, поки нема реальних даних.

Одна команда `imu` з підкомандами (розділ 9).

## 2. Жорсткі правила

1. **Тільки слухати порт.** На тому ж USART1 модуля сидять OTA-бутлоадер і командний парсер. Випадковий байт може зіпсувати прошивку. Тому:
   - `SerialSource` не має методу запису, а об'єкт порту прихований;
   - порт створюється закритим, налаштовується і тільки потім відкривається: DTR і RTS вимкнені, flow control вимкнений, доступ ексклюзивний;
   - тест `tests/test_listen_only.py` запускає справжній pyserial на віртуальному порту (pty), у якому `write` і `send_break` підмінено на помилку. Інший тест шукає в `src/` будь-які виклики запису в порт.
2. **Без SWD.** Жодного pyOCD, флешу, option bytes, RDP. `swd_probe.py` не запускати і не змінювати.
3. **Калібрація тільки на хості.** Це поправка до потоку, модуль не змінюється.
4. **Нічого не припускати про осі, одиниці і системи координат.** Усе перевіряється по даних, звітується і вмикається тільки після підтвердження.
5. **Сирі значення незмінні.** Калібрація і вирівнювання осей пишуться в окремі колонки.
6. Пакети ставляться тільки в `.venv` проєкту через `uv`. Системний pip і `~/embed/imu/uart/.venv` не чіпати.

## 3. Встановлення і запуск

```bash
cd ~/embed/imu/eps_imu_demo
uv sync                 # ставить залежності в .venv проєкту
uv run imu --help       # список команд
uv run pytest           # тести (137 шт., ~15 с)
```

Залежності: numpy, pyarrow, pyserial, rerun-sdk 0.38.1, scipy, matplotlib. Для розробки: pytest і ruff.

`vendor/mtdata2_decoder.py` лишається самостійним скриптом, який можна запускати напряму. Водночас пакет імпортує його як модуль: папка `vendor/` додається до шляху через `dev-mode-dirs` у `pyproject.toml`.

Якщо в shell активовано ROS, його плагіни pytest ламаються. У `pyproject.toml` вони вимкнені.

## 4. Пристрій коротко

Повний опис - у `docs/module-context.md`.

```
H743 USART1 -> ADM3232E (RS-232) -> USB-RS232 (SP3232 + CP2102) -> /dev/ttyUSB0 -> imuview
```

- 115200 8N1, модуль шле дані сам, без запиту.
- Протокол Xsens MTData2: `FA FF 36 LEN payload CS`.
  - Контрольна сума: `sum(FF..CS) & 0xFF == 0`.
  - Числа big-endian.
  - `LEN = 0xFF` означає розширену довжину (ще 2 байти).
- Кадр IMU (94 байти, LEN 89), блоки по порядку:

| XDI | що | тип |
|---|---|---|
| 0x2030 | Euler roll, pitch, yaw (обчислює сама прошивка) | 3 x float32 |
| 0x4020 | Acceleration | 3 x float32 |
| 0x8020 | RateOfTurn (гіро) | 3 x float32 |
| 0xE010 | StatusByte: біт0 selftest, біт1 filter valid, біт2 GNSS fix | 1 байт |
| 0x5040 | LatLon | 2 x float32 |
| 0x5020 | AltitudeEllipsoid | float32 |
| 0xD010 | VelocityXYZ | 3 x float32 |
| 0x2060 | нестандартний, зміст невідомий | float32 |

- Окремо 5 разів на секунду йде кадр GpsSol (0x8840, 60 байтів, LEN 55).
- У потоці немає часової мітки, лічильника пакетів, магнітометра і кватерніона.

## 5. Архітектура

### 5.1 Потік даних

```
Source ──bytes──> Demux ──frames──> Parser ──messages──> Calibration ──> BoardAlignment
                                                                            │
         ┌──────────────────────── Router (publish/subscribe) <─────────────┘
         │
         ├─> Estimators (Mahony/Madgwick: vehicle + по одному на кожну IMU) ──> State
         ├─> Recorder  (raw.bin, *.parquet, events.jsonl, meta.json)
         └─> Viewer    (Rerun)
```

Живий порт, симулятор, повтор сесії та імпорт файлів проходять через один і той самий `Pipeline`. Відрізняється тільки `Source`.

### 5.2 Модулі (`src/imuview/`)

| файл | що робить |
|---|---|
| `messages.py` | Типи повідомлень: `ImuSample`, `GnssFix`, `GnssRaw`, `RawBlock`, `Command`, `Event`, `State`. Поля часу, `STREAMS` (яке повідомлення в який parquet). |
| `sources.py` | Джерела байтів або повідомлень: `SimSource` (протоколи `ref` і `mtdata2`), `SerialSource` (тільки читання), `RawFileSource` (raw.bin сесії), `BytesSource` (сирий дамп без часу), `MessageSource` і `csv_messages` (CSV і сесії без байтів). |
| `protocol.py` | `Demux` запускає кілька фреймерів на одному потоці байтів. Також тут фреймери ref, NMEA, UBX, референсний парсер `RefParser` і реєстр `PARSERS`. |
| `protocol_mtdata2.py` | `Mtdata2Framer` і `Mtdata2Parser` (обгортка над `vendor/mtdata2_decoder.py`), `RepeatDetector`, кодувальник кадрів для симулятора і тестів. |
| `calibration.py` | Клас `Calibration`: завантаження і збереження JSON, sha256, застосування `a_cal = M (a - b)`, `w_cal = w - bias`. |
| `pipeline.py` | Конфіг за замовчуванням, `Router`, `Pipeline`. Послідовність: парсер, калібрація, вирівнювання, оцінювачі. Також клавіші, події, статистика, запис. |
| `fusion.py` | Mahony, Madgwick, passthrough. `IntervalClock` (dt з часу пристрою або хоста з обмеженням по медіані), `GyroCalibrator` (клавіша `c`). |
| `frames.py` | Уся математика систем координат: кватерніони, Euler, board alignment, tare, геодезія, ENU/NED. |
| `logger.py` | Папка сесії, `raw.bin`, запис потоків (Arrow, потім parquet), відновлення після збою. |
| `viewer.py` | Rerun: 3D, графіки, журнал подій, таймлайни. |
| `framing_analysis.py` | Аналіз, чому кадри не проходять контрольну суму (команда `imu framing`). |
| `calib_tools.py` | Етапи калібрації 0-2: `check`, `gyro`, `axes`, завантаження сесій, CSV і дампів, звіти. |
| `cli.py` | Команда `imu` і всі підкоманди. |

### 5.3 Етапи конвеєра детально

**Source.** `read()` повертає список `Chunk(pc_rx_time_ns, data)` (байти з моментом отримання) або готові повідомлення (їх називаємо "injected"). Атрибути джерела:
- `protocol` - симулятор сам каже, який у нього формат;
- `baud` - потрібен для відновлення часу;
- `time_source` - `host` або `synthetic`.

**Demux.** Шукає синхробайти всіх фреймерів. У кожній позиції питає фреймери:
- кадр з правильною сумою - віддає далі;
- кадру не вистачає байтів - чекає наступного chunk;
- погана сума - зсувається на 1 байт (ресинхронізація).

Байти поза кадрами рахуються як "unclaimed". Для кожного кадру Demux запам'ятовує `bytes_after`: скільки байтів прийшло після його кінця в тому ж буфері.

**Parser (`mtdata2`, за замовчуванням).**
- Блоки розбирає `vendor.parse_payload`, таблиця XDI не переписувалась.
- Фреймер повторює правила vendor `Framer` і на всіх legacy-дампах дає ідентичні лічильники. Це перевіряє тест.
- Результат:
  - `ImuSample` - accel, gyro, `euler_deg`, `status`, `extra` (0x2060 і всі невідомі блоки);
  - `GnssFix` - з кожного IMU-кадру. `fix_type` = 3, тільки якщо встановлено біт 2 статусу, інакше 0, і тоді координати ~29.9999 є заглушкою;
  - `GnssRaw` - GpsSol як hex, без розбору;
  - `RawBlock` - невідомі блоки кадрів без IMU. Нічого не губиться.
- Біти XDI записуються для кожного блоку: 0-1 точність, 2-3 система координат. Поки що все float32/ENU. Блок з ненульовими бітами зберігається сирим, і генерується попередження.
- Відсутність IMU-плати: якщо всі компоненти accel і gyro за модулем менші за 1e-9, в журналі з'являється попередження. У реальному dry run там не рівно 0, а стале ~1e-14.
- Повтори: `accel_repeat` і `gyro_repeat` стають True, якщо значення точно дорівнює одному з 4 попередніх (докладніше в розділі 11).
- Якщо колись з'являться 0x1020 PacketCounter або 0x1060 SampleTimeFine, вони стануть `seq` і часом пристрою.
- Статистика в `meta.json`: кадри за MID, погані суми за MID/LEN, extended-кадри, лічильники XDI, біти XDI, значення статусу, повтори, розриви `seq`.

**Calibration.** Працює в рідній системі координат сенсора, до вирівнювання осей. Заповнює `accel_cal` і `gyro_cal`, `accel` і `gyro` не змінює. Зміна board alignment не робить калібрацію недійсною.

**BoardAlignment.** Переводить вектори сенсора в осі корпусу (FRD) і заповнює `accel_body` і `gyro_body`. Бере каліброване значення, якщо воно є, інакше сире. Далі застосовує поворот `board_alignment_deg` з конфігу і level trim з калібрації.

**Estimators.** Mahony (за замовчуванням), Madgwick або passthrough. Один оцінювач для "vehicle" і по одному діагностичному на кожну IMU. Використовують `*_body`. Результат - `State` (кватерніон корпус -> NED).

**Recorder і Viewer.** Підписуються на Router. Recorder пише все, Viewer показує. Детальніше в розділах 8 і 7.

## 6. Час без годинника пристрою

У кожного повідомлення є:
- `mcu_time_us` - час пристрою, для MTData2 зараз None;
- `pc_rx_time_ns` - момент, коли прийшов USB-chunk (monotonic);
- `host_time_ns` - відновлений час самого кадру;
- `time_source` - `device`, `host` або `synthetic`.

Властивість `t_us` означає: час пристрою, якщо він є, інакше host-час.

**Відновлення host-часу.** Час кадру = час chunk мінус (байти після кінця кадру) x 10 / baud. Без цього всі кадри одного chunk мали б однаковий час. Формула вважає лінію завантаженою повністю, а реальна завантаженість 85%. Тому всередині chunk інтервали виходять стиснутими приблизно на 15%.

**dt для фільтрів.**
- Час пристрою використовується як є. Інтервал понад 0.1 с пропускається.
- Host-час обмежується до [0.5, 3] x медіана останніх 51 інтервалу.
- Інтервал понад 3 x медіана записується в журнал як "time gap". Це нормально: погані кадри відкидаються, і на їх місці лишаються дірки до ~70 мс.

**Синтетичний час** (`imu import raw`). У дампі нема часу, тому час рахується з позиції байта: байт / byte_rate. Byte rate дорівнює baud/10 або задається через `--duration`.

**CSV від `mtdata2_decoder.py`.** Колонка `t` - момент обробки chunk. Vendor-декодер читає порт шматками ~0.2 с, тому час грубий. При імпорті рядки одного chunk розносяться за розмірами кадрів (94 і 60 байтів). Це наближення: байти поганих кадрів у CSV не збережені.

**Таймлайни Rerun.**
- `time` - час пристрою або host-час, від 0 з першого повідомлення;
- `pc_time` - настінний час приходу chunk.

## 7. Системи координат

| система | де | опис |
|---|---|---|
| сенсор | `accel`, `gyro`, `*_cal` | рідні осі потоку. Напрямки ще НЕ підтверджені, їх визначає `imu calib axes` |
| корпус (body) | `*_body`, `State.q` | FRD: x вперед, y вправо, z вниз |
| світ | `State.q`, 3D-сцена | локальна NED: північ, схід, низ |
| Euler пристрою | `euler_deg` | гіпотеза: сенсор -> ENU, ZYX (як у Xsens). Підтверджено 0.01° на одному записі з нахилом ~3°, чекає 6 положень |

Ще кілька правил:
- Кватерніон записується як (w, x, y, z), множення Гамільтона, обертає корпус у світ.
- Euler хоста: yaw, pitch, roll (ZYX).
- Accel вимірює питому силу: плата в спокої лежить рівно і показує (0, 0, -g) у FRD. Сирий потік модуля в спокої показує +9.8 по z сенсора.
- `board_alignment_deg = [roll, pitch, yaw]` - поворот сенсор -> корпус: `v_body = R v_sensor`.

**Увага.** За замовчуванням стоїть [180, 0, 0]: сенсор модуля в спокої показує +g по z, тобто z дивиться вгору, і поворот на 180 градусів по roll приводить його до FRD. Це тимчасово: x і y ще не перевірені, тому нахили і yaw моделі "host" можуть бути дзеркальними, поки `imu calib axes` не підтверджено. Графіки сирих даних і Euler пристрою від цього не залежать.

Yaw без магнітометра дрейфує. Клавіша `c` уповільнює дрейф, але не зупиняє. Це фізика, а не баг.

## 8. Сесія: що записується

Кожен запуск із записом створює папку `logs/YYYY-MM-DD_HH-MM-SS_<мітка>/`:

| файл | вміст |
|---|---|
| `raw.bin` | Кожен отриманий байт. Записи `[pc_rx_time_ns: u64][len: u32][bytes]`, little-endian. Це першоджерело: з нього все можна перерахувати. |
| `imu.parquet` | Один рядок на семпл. Час: `mcu_time_us, pc_rx_time_ns, host_time_ns, time_source, seq`. Сирі `accel_*, gyro_*` (як надіслав пристрій, ніколи не змінюються). Каліброване `accel_cal_*, gyro_cal_*`. У корпусі `accel_body_*, gyro_body_*`. Від пристрою `euler_deg_*, status, extra` (JSON). Позначки `accel_repeat, gyro_repeat`. |
| `gnss.parquet` | GnssFix. Без `fix_type` >= 2 координати не використовувати. |
| `gnss_raw.parquet` | GpsSol як hex. |
| `raw_blocks.parquet` | Невідомі блоки кадрів без IMU (поки порожньо). |
| `state.parquet` | Орієнтація від оцінювачів. `source` = `vehicle` або `imu<k>`. |
| `commands.parquet` | Натискання клавіш (`c`, `t`), щоб повтор сесії їх повторив. |
| `events.jsonl` | Журнал подій: перші кадри, нові XDI, погані суми, розриви часу, відсутність IMU... |
| `meta.json` | Мітка, джерело, парсер, оцінювач, калібрація (шлях і sha256), конфіг, конвенції, git commit, час початку і кінця, статистика. |
| `record.rrd` | Запис Rerun (тільки з `--rrd`). |

Під час запису потоки пишуться як `*.arrows` і скидаються на диск раз на секунду. При збої втрачається не більше ~1 с. Після нормальної зупинки вони конвертуються в parquet. `imu info` дооформлює сесію після збою.

Колонки, що не застосовуються, мають значення null. Кожен потік лежить в окремому файлі.

## 9. Команди

Усі команди запускаються як `uv run imu <команда>`. Спільні опції:
- `--config config.toml` - файл налаштувань;
- `--calib file.json` - застосувати калібрацію (сире лишається сирим);
- `--label мітка` - потрапляє в `meta.json` і в назву папки;
- `--no-viewer` - без Rerun;
- `--no-record` - без запису;
- `--rrd` - ще й файл Rerun.

### Живий пристрій

```bash
uv run imu live                          # Rerun + запис сесії
uv run imu live --no-record              # тільки подивитися
uv run imu live --seconds 60 --label test --no-viewer
uv run imu live --calib calib/imu_calib.json
```

Клавіші:
- `c` - bias гіро: тримати нерухомо 3 с;
- `t` - tare: поточна орієнтація стає нульовою, лише для показу;
- `r` - почати або зупинити запис (кожен раз нова сесія);
- `q` - вихід.

### Калібрувальні записи (без Rerun, зупинка по часу або Ctrl+C)

```bash
uv run imu calib record --label still --seconds 60
uv run imu calib record --label pose_left --seconds 15 [--viewer]
```

### Повтор і перерахунок

```bash
uv run imu replay logs/<сесія>                  # у реальному часі, з Rerun
uv run imu replay logs/<сесія> --fast --speed 4
uv run imu replay logs/<сесія> --calib calib/new.json --record   # зберегти як нову сесію
uv run imu reparse logs/<сесія> --calib calib/new.json            # headless, нова сесія
uv run imu reparse logs/<сесія> --out /шлях/до/папки --parser mtdata2
```

- Якщо в сесії є байти, повтор іде з `raw.bin` і повторює натиснуті клавіші.
- Для CSV-сесій (без байтів) повтор іде зі збережених повідомлень, а калібрація і вирівнювання перераховуються.

### Імпорт старих файлів `mtdata2_decoder.py`

```bash
uv run imu import csv data/legacy/still.csv --label still
uv run imu import raw data/legacy/still.bin --label still --duration 13.5
uv run imu import raw dump.bin --label x --byte-rate 9760
```

- **CSV:** рядки з порожнім `ax` - це кадри GpsSol. Вони йдуть у `gnss_raw` без байтів, бо в CSV їх нема.
- **Raw:** час синтетичний. Без `--duration` і `--byte-rate` використовується 11520 B/s, тоді як реальний потік ~9760 B/s.

### Аналіз кадрів

```bash
uv run imu framing data/legacy/still.bin --duration 13.5 [--out report.json]
uv run imu framing logs/<сесія>          # тривалість береться з raw.bin
```

Звіт JSON містить:
- валідні і погані кадри за MID/LEN, хибні синхронізації, extended-кадри;
- обрізані і повнодовжинні погані кадри;
- розклад байтів і найчастіші "зайві" вставки;
- ймовірність поганого кадру залежно від позиції після GpsSol, довжини серій поганих кадрів;
- перевірку "CS = правильна сума кадру на відстані ±k";
- повтори payload, правдоподібність |a| у поганих кадрах.

### Калібрація (етапи 0-2)

```bash
uv run imu calib check  <сесії | CSV | дампи ...>
uv run imu calib gyro   logs/*_still logs/*_rot_*
uv run imu calib axes   logs/*_pose_* [--poses level,back,left,right,nosedown,noseup]
uv run imu calib axes   logs/*_pose_* --write config.toml     # тільки після підтвердження
```

- **check:** тривалість, частота, інтервали, розриви, частка рядків без IMU, заморожені осі, частка повторів, |a| і одиниці, спокій, відсутність плати, статуси, 0x2060, Euler проти accel у 4 гіпотезах, погані суми.
- **gyro:** bias, шум, bias на перших і останніх 10 с (дрейф у сигмах). Підказка одиниць за рівнем шуму. Для `rot_*`: кут з інтегрованого гіро проти кута зі зміни Euler, їх відношення (масштаб) і вісь обертання в осях сенсора.
- **axes:** середній accel у кожному положенні. Підгонка повороту (Kabsch), найближча перестановка зі знаками, таблиця "вісь сенсора -> вісь корпусу", `board_alignment_deg`, залишковий нахил монтажу, мінімальний кут між положеннями, які положення не покрито. Перевіряє праворукість осей.
- Положення беруться з мітки сесії (`pose_left` -> left) або з `--poses`. Назва означає сторону, що дивиться ВНИЗ, як у Mission Planner.
- Звіти (`.md` + `.json`) пишуться в `calib/reports/<дата>/`.

## 11. Що вже відомо про пристрій з даних

Перевірено на `data/legacy/` (still 13.5 с, два дампи ~35 с і ~13 с).

- **Потік.** 100 IMU-кадрів/с і рівно 5 GpsSol/с. Лінія завантажена на 85%.
- **Погані суми: 30-40% IMU-кадрів.** Причина - гонка буферів у прошивці, а не лінія:
  - погані кадри мають повну довжину, обрізаних нема;
  - вміст правдоподібний: той самий розподіл |a|, неперервний Euler;
  - CS поганого кадру часто дорівнює правильній сумі кадру, що йде на 2 пізніше (у 25-40% поганих кадрів, при рівні випадковості <1%);
  - перші 3 кадри після кожного GpsSol погані на 85-97%.

  Це схоже на ping-pong буфер, який переписується, поки DMA його ще відправляє.
  - **Рішення:** погані кадри відкидаються. Лишається ~61 IMU-кадр/с.
- **Повтори.** Accel, gyro і Euler незалежно повторюють значення кадру, що був на 2 раніше, у 13-17% кадрів. Прошивка оновлює їх різними задачами.
  - **Рішення:** повтори позначаються і не беруться в оцінки шуму, bias і стабільності.
- **Сталий 25-байтовий блок** `fa 70 54 03 11 00 00 87 1e c8 2a ...` після кожного другого GpsSol. Це не Xsens-кадр, зміст невідомий.
- **Хибні синхронізації** `FA FF` всередині даних: ~0.
- **Dry run** (плата IMU відключена): accel і gyro дорівнюють сталим ~1e-14, а не 0. Прошивка щось обчислює над сирими даними. Це аргумент "за" в питанні, чи калібрує прошивка сама.
- **Одиниці accel: м/с^2** (|a| в спокої 9.8216).
- **Одиниці гіро:** шум 1.3e-3 правдоподібний для рад/с. Масштаб перевіримо на `rot_*`.
- **Euler пристрою** в спокої узгоджується з accel у гіпотезі ENU/ZYX з похибкою 0.01°. Тест слабкий, бо нахил був лише ~3°.

**Ще не перевірено:**
- осі сенсора відносно корпусу;
- масштаб гіро;
- зміст 0x2060;
- чи калібрована вже прошивка;
- поведінка на живому порту.

## 15. Якщо щось не працює

- **`could not open port` / `Device or resource busy`.** Порт уже читає інша програма (наприклад `mtdata2_decoder.py`). Порт відкривається ексклюзивно: одночасно може бути тільки один читач.
- **Немає доступу до `/dev/ttyUSB0`.** Користувач має бути в групі `dialout`.
- **Rerun не відкривається.** Запусти з `--no-viewer` і перевір запис. Або додай `--rrd` і відкрий файл пізніше.
- **Багато "time gap" у журналі.** Це нормально: відкинуті погані кадри лишають дірки до ~70 мс.
- **Сесія після збою без parquet.** `uv run imu info logs/<сесія>` її дооформить.
- **`uv sync` видалив пакет.** Усі потрібні пакети мають бути в `dependencies` у `pyproject.toml`.

## 16. Мульти-модульність і GUI (додано 2026-09-30)

### 16.1 Кілька модулів

- Кожне повідомлення має `module_id` (0 - USB-serial, 1..255 - модулі по мережі; їх роздає майстер-ESP за порядком підключення).
- `multi.py`: `MultiPipeline` тримає по одному `Pipeline` на `module_id`, створює їх, щойно id з'являється в потоці. Усі пишуть у один `Router` і в **одну сесію**: у кожному рядку parquet є колонка `module_id`. У `raw.bin` id модуля лежить у старшому байті поля довжини запису (старі файли читаються як модуль 0).
- `UdpSource` (`sources.py`): слухає UDP, лише читає. Формат датаграми в `netproto.py`: `['IV'][версія u8][module_id u8][seq u16 LE][len u16 LE][байти MTData2]`, один кадр на датаграму. Биті датаграми (magic, версія, довжина) лічаться й відкидаються, пропуски `seq` рахуються як втрати. Адреса й порт: `[network]` у конфігу (типово 0.0.0.0:5005).
- Перевірка без заліза: `uv run imu sim --protocol mtdata2 --modules 3 --gps --fast --seconds 6`, `uv run imu net`, `uv run python tools/udp_master_sim.py --modules 3 --gps` (імітує майстер, лежить поза `src/`, бо сама програма нічого не надсилає).
- Імена модулів: `[modules.names]` у конфігу, типово "Module N".

### 16.2 Калібрація акселерометра (calib_tools.py)

```bash
uv run imu calib accel logs/*pose_level logs/*pose_back logs/*pose_left logs/*pose_right logs/*pose_nosedown logs/*pose_noseup --config config.toml
uv run imu calib level logs/*pose_level --accel-json calib/reports/<дата>/accel_<час>.json --config config.toml
uv run imu calib gyro logs/*_still
uv run imu calib report      # md + PNG з найновіших результатів
uv run imu calib apply       # calib/imu_calib.json
```

- Модель `a_cal = M (a_raw - b)` у системі осей сенсора. Підгонка по норми: стоячий сенсор має давати `|a| = g`, тож поза не мусить бути ідеальною.
- `six` (типово): `b` + діагональна `M`, 6 параметрів. `nine`: симетрична `M` (додає міжосьові члени), лише при >= 12 помітно різних положеннях і коли Якобіан спостережуваний (число обумовленості < 100), інакше помилка з поясненням. `axis`: простий по-осьовий метод для порівняння (на нахилених положеннях дає гірший результат).
- Перевірки (у дусі Mission Planner, пороги наші): зсув < 3.5 м/с^2, масштаб 0.8-1.25, `|a|` у межах 1% від g у кожному положенні, положення різні, кожне було нерухомим. При 6 положеннях і 6 параметрах підгонка точно визначена, тому залишок після калібрації нічого не доводить (звіт це каже); для перевірки потрібне додаткове положення.
- `level`: крен і тангаж, які роблять рівне положення `(0, 0, -g)` у системі корпусу (з урахуванням `board_alignment_deg`).
- На записах користувача (`logs/*pose_*`, `still`): зсуви ~0.003 м/с^2, масштаби 0.998-1.000, `|a|` сирий відрізняється від g менше ніж на 0.21%. Модуль фактично вже відкалібрований з заводу. Результат лежить у `calib/imu_calib.json`. Кут нахилу рівного положення 2.6 градуса (близько до 2.1 з `calib axes`).

Дизайн (темно-синя тема з жовтим акцентом, Inter і JetBrains Mono з `assets/fonts` разом з ліцензіями OFL, іконки Lucide з `assets/icons`, без мережі):
- Віджети не зникають, а блокуються. Стан зʼєднання: `disconnected -> connected -> running` (`AppController.conn_state`). "Під'єднати" відкриває джерело і показує дані, нічого не пишучи; "Старт" починає лог, якщо увімкнено "Писати лог"; "Стоп" закриває лог. Під час `running` порт, транспорт і "Писати лог" заблоковані, горить REC.

- Вкладка "Калібрація": степер кроків (клік по виконаному кроку переробляє його), велике 3D-превʼю з поточною орієнтацією і напівпрозорою цільовою (зеленіє, коли збіглись, допуск 12 градусів), чипи нерухомо/рух, прогрес, плитки `|a|`, розкид і відхилення з порогами, міні-графік `|a|` з лінією 9.81, підсумок (зсув, масштаб, гіро, вирівнювання, залишок по кроках) з "Відкинути" і "Зберегти і застосувати".
- Менеджер моделей: STL копіюється в `QStandardPaths.AppDataLocation/models`, метадані в `models.json` (`id, name, file, builtin, scale[x,y,z], pivot[x,y,z], forward_axis, up_axis`). Перший запуск переносить `models/` з дистрибутива в бібліотеку. Вбудовані моделі не змінюються і не видаляються, але дублюються. Зміни діють на сесію тільки після "Зберегти". Битий файл дає заглушку, битий `models.json` відкладається як `models.json.bad`.

Що де:
- Орієнтація завжди за кватерніоном фільтра (корпус FRD -> NED, у сцені x схід, y північ, z вгору).
- З валідним фіксом GPS модель рухається, лишає до 8 примарних копій за вікно `trail_seconds` (2 с) і лінію сліду. Без GPS рухів нема, малюється стрілка сили (0.3 м на м/с^2, максимум 4 м); "Віднімати гравітацію" дає `free_acc`.
- "Читати GPS" вимикає тільки показ руху; лог пишеться завжди.
- Орієнтація моделі задається віссю носа і віссю верху самого STL (`forward_axis`, `up_axis`; з них виходить поворот у осі корпусу: ніс +x, права сторона +y, низ +z). Для `shahed.stl` це ніс +Z, верх +X (STL стоїть на хвості), для `IAI_scout.stl` ніс -Y, верх +Z. Орієнтацію носа перевірено на знімках. Старий формат `models/models.toml` з `rotation_deg` читається й далі (тести, перший запуск).
- Linux під Wayland: `gl_common.configure_platform()` форсує X11 (xcb) і GLX, інакше PyOpenGL каже "no valid context". На Windows нічого не потрібно.
- Rerun лишається інженерним виглядом для одного модуля: `imu live | sim | replay`. Окремого `--rerun` у GUI нема: Rerun-в'ювер не знає про `module_id`.

### 16.4 Пакування

`uv run pyinstaller packaging/imuview.spec --noconfirm`. Результат: `dist/imuview.exe` (Windows) або `dist/imuview` (Linux), один файл, без консолі; `models/`, `config.example.toml` і `vendor/mtdata2_decoder.py` всередині. `.exe` треба збирати на Windows (PyInstaller не кросс-компілює). Linux-збірка перевірена: запускається й записує сесію; моделі, декодер і Qt-плагін є в архіві (`pyi-archive_viewer`).

### 16.5 Чого ще нема

- Справжніх прошивок ESP (slave ESP-01, master ESP32-S3): формат датаграми готовий, прийом перевірено лише на симуляторі й на localhost.
- Перевірки на живому мережевому потоці і на Windows.
- Калібрації кількох модулів окремо в GUI: майстер калібрує активний модуль, результат застосовується до всіх (один `calib/imu_calib.json`). Калібровка по `module_id` (`MultiPipeline(calibrations={id: ...})`) у логіці є, у GUI її поки нема.
